Design research — nothing built yet

An attendance verification system, thought through in plain words

You sketched a flow: login → device check → GPS → geofence → face match → liveness → server check → attendance marked. Below is a plain-language walk-through of whether that's realistic, what each step should actually do, and what to build first versus later — grounded in what's already in this codebase.

Short version

Yes, this is buildable — every piece is a known, off-the-shelf technique. But the full flow (face match + liveness + device lock) is heavy: expensive, easy to get wrong, and hard on old phones and weak village networks. The honest-evidence version — login, GPS, a stored selfie, and a server that double-checks everything — already blocks the main way people cheat attendance (marking it from home). Add face matching and liveness later, only if that alone isn't enough.

The one rule that matters more than any single step: the phone captures evidence, the server decides. Never trust a "yes, verified" flag the app sends — recompute it server-side from the raw GPS numbers and the raw photo, every time.

Update: sections 18–23 extend this into a full working-time system — school timing rules, late/early/half-day math, and a direct answer to whether GPS needs to run all day (it doesn't).

01 — Feasibility

Yes, it's technically doable

Nothing in that flow needs new invention. GPS location, geofences, face matching, and liveness checks are all mature, well-documented building blocks — libraries and SDKs exist for every single one. The hard part was never "can this be built."

The hard part is: will it work reliably for a teacher standing in a school courtyard, on a three-year-old Android phone, on patchy 3G, at 8:55am when class is about to start? That's an operations and product problem, not a technology one — and it's what most of this document is actually about.

03 — Location

Handling GPS inaccuracy, and geofencing a school

A phone's GPS doesn't give one exact point — it gives a point plus a confidence radius ("you are here, give or take 40 metres"). That radius gets worse indoors, near tall buildings, or with a cheap GPS chip.

  • Set an accuracy floor. If the reported accuracy is worse than, say, 100 metres, don't accept it — ask the app to wait a couple of seconds and try again, and use the best of the last few readings.
  • Make the geofence bigger than the GPS error. If typical error is ±40–60m, a school geofence of 150–200m radius absorbs that noise. A tight geofence the same size as the campus will reject real teachers standing on it.
  • Never trust the phone's own "inside the fence" answer. The app can compute a preview for instant feedback, but the number that counts is the one the server computes itself from the raw coordinates.

Location spoofing

Apps exist that fake a phone's GPS (a "mock location"). Two practical defenses, used together rather than relying on either alone:

  • Mock-provider flag. Android tells the OS whether a location came from a fake provider — check it and flag (or reject) any reading that's flagged. iOS doesn't expose an equivalent, so treat this as a useful signal, not a guarantee.
  • Impossible-travel check. If the same teacher's last check-in was 200km away 5 minutes ago, that's not a GPS-noise problem — flag it for review regardless of what the mock-provider flag says.

Geofence shape: a circle (centre point + radius) is enough for almost every school and is trivial to store and compute. Reach for a custom-drawn polygon only for the rare oversized or oddly-shaped campus — it's not worth the extra complexity as a default.

04 — Identity

Face verification, and stopping a photo standing in for a face

How face verification works, in plain words

A teacher enrolls once with a clear reference selfie (ideally with an admin present, so the reference photo itself can be trusted). On every check-in, the app captures a new selfie. A face-matching model turns each photo into a string of numbers — a "fingerprint" of that face — and the system checks how close the two fingerprints are. Close enough, above a set threshold, counts as a match.

OptionTrade-off
Cloud API (e.g. a hosted face-matching service) Very accurate, but costs money per check, needs internet every time, and sends teachers' faces to a third-party server — a real concern once "government school" and "data localisation" are both in the picture.
On-device model (runs inside the app itself) Free per use, works with no internet, keeps the photo on the phone. Slightly less accurate than the best cloud services, but more than enough for this use case. Recommended for cost, offline-capability, and privacy — especially at government-school scale.

Stopping someone from holding up a photo or playing a video

This is exactly the job of liveness detection — proving the thing in front of the camera is a real, present person, not a printed photo or a screen playing a video.

  • Passive liveness — the model inspects a single shot for giveaways: screen glare, flat texture, moiré patterns from a phone screen. No effort from the teacher, but it's a quiet arms race against ever-better fakes.
  • Active liveness — the app asks for one small, randomly-chosen action in the moment (blink, turn your head, smile). Costs the teacher two or three seconds, but a pre-recorded video can't fake a prompt it hasn't seen yet.
Recommendation

Active liveness with one random simple prompt. It needs no special hardware or heavy model, and for a low-cost-device, low-tech-literacy audience it's the most reliable trick for the least engineering effort.

Is liveness even necessary?

Only in proportion to whether face matching is doing real work. Skip face matching in the MVP (see §14) and liveness has nothing to protect — it's meaningless on its own. The moment face matching is added, liveness stops being optional: without it, anyone can hold up a printed photo of the teacher and pass.

05 — Device & session

Stopping attendance from an unauthorized device

The baseline control already exists: a password/PIN login with short-lived tokens. On top of that:

  • Record a device identifier the first time a teacher signs in.
  • When a check-in arrives from a device that isn't the recognized one, don't silently allow it — either require a fresh login (already enforced by session expiry) or notify the teacher and flag it for admin review.

A common alternative in Indian government attendance apps is a hard device lock — the account only ever works on one phone. It's a strong guarantee, but it creates real support load (lost phones, phone upgrades, repairs), and none of that maps to fixing an actual fraud pattern unless you've observed one. Flag unrecognized devices; don't hard-lock unless a specific problem shows up that justifies the support cost.

06 — The one rule that matters most

Server-side validation: the phone proposes, the server decides

A phone app can be modified, rooted, or run through a tool that fakes what it reports. So anything the app itself calculates and simply tells the server — "I'm inside the fence," "the face matched" — can be lied about. The fix is structural, not a patch:

  • The server only accepts raw evidence: GPS coordinates + accuracy, the actual selfie bytes, a client timestamp, device info.
  • The server recomputes the geofence distance itself, from the school's stored coordinates — it never reads a client-sent "inside: true".
  • The server runs (or independently checks) the face match itself — it never accepts a client-sent "matched: true".
  • The server stamps the official time using its own clock, never the phone's — phone clocks can be changed by the user.
  • The server rejects stale or duplicate submissions (a timestamp/nonce check), so old evidence can't be replayed later.

07 — Edge cases

What should happen when something goes wrong

Two failure modes are equally bad here: a system that silently marks someone "present" when it shouldn't, and one that hard-blocks a genuine teacher with no way forward — attendance affects pay and service record, so a human fallback matters as much as the automated check.

SituationWhat the system should do
GPS unavailableAsk the teacher to enable location and retry. Don't mark attendance with no location at all — offer a manual entry, clearly flagged "no GPS" for admin review.
GPS accuracy is poorRetry a few times / wait briefly for a better fix. If it's still poor after several tries, accept the check-in but mark it "low confidence" for admin review rather than blocking a genuine teacher.
Teacher is just outside the fenceOffer "mark anyway" with an optional short reason, auto-flagged for admin review — not a hard block.
No internetQueue the attempt on-device with all the same evidence and a local timestamp; auto-submit on reconnect. Show "pending sync" until the server confirms with its own timestamp.
Face verification failsAllow a couple of retries — bad lighting is extremely common. After repeated failure, fall back to a flagged manual/admin-confirmed path instead of blocking attendance entirely.
Liveness failsSame pattern: limited retries, then the same flagged fallback path.
Location spoofing suspectedBlock the automatic mark and flag it prominently for admin review — never let a suspected spoof through silently.
Unrecognized device usedRequire a fresh login, notify the real teacher, and optionally require admin approval before that device can check in again.

Retention note

Keep a raw selfie only as long as it's actually useful for resolving a dispute (e.g. 30–90 days), then auto-delete it. The much-less-sensitive match score/embedding can be kept longer for audit purposes if needed — minimize what's held, not what's computed.

09 — Teacher experience

Opening the app to attendance marked

The whole happy path should take under 10–15 seconds:

  1. Teacher opens the app, already signed in.
  2. Taps "Mark attendance."
  3. App silently gets a GPS fix; if accuracy is poor, it says so and waits a moment rather than failing immediately.
  4. (Phase 2+) Front camera opens, teacher looks at the phone; a quick prompt appears if liveness is on ("blink").
  5. "Verifying…" for a second or two.
  6. Clear result: "Attendance marked at 9:02 AM" — or, on a flagged case, a plain explanation ("You're a bit outside the school boundary — mark anyway and let the admin know why?") rather than a dead-end error.

10 — Admin tools

What a school/district admin needs

  • Set each school's geofence centre + radius (ideally by dropping a pin on a map).
  • Enroll or re-enroll a teacher's reference photo.
  • Review a queue of flagged check-ins (poor GPS, outside fence, spoofing suspected, unrecognized device) and approve/reject with a logged reason.
  • Manage recognized devices per teacher.
  • Browse attendance by date, school, or teacher; export for whatever the state education department already asks for.

11 — Reports & analytics

What's worth surfacing

  • Daily and monthly attendance percentage, per teacher / school / district.
  • Late-arrival trends over time.
  • A flagged-incident log, for accountability review.
  • CSV/PDF export shaped to match existing government reporting formats, so a school isn't doing the same data entry twice.

12 — Privacy & security

Face data is sensitive personal data

Under India's DPDP Act, 2023, biometric data counts as sensitive personal data — that has real, specific implications for this system, not just general good practice:

  • Clear consent at enrollment, with the purpose stated plainly (attendance only).
  • Data minimization — store the minimum needed; prefer the numeric embedding over the raw photo wherever the raw photo isn't specifically needed.
  • Encryption in transit and at rest.
  • Access control — only the roles that need to see raw evidence (e.g. admins resolving a flagged dispute) can see it.
  • A retention and deletion policy, actually enforced, not just written down.
  • Data localization — if a cloud face-matching API is ever used, check where it actually processes the data. This is one more reason on-device processing is the better default for a system built around government schools.

13 — Real-world risks

What actually tends to break, in this specific context

  • Old, budget Android phones with weak cameras and noisier GPS chips — design for the low end, not a flagship.
  • Patchy or absent mobile network in rural areas, right at check-in time — this has to be offline-first, not offline-tolerant.
  • Face-match false rejects from poor lighting, glare on spectacles, or a reference photo that's years old.
  • Recurring cloud API cost, multiplied across thousands of schools and lakhs of daily check-ins — this is the strongest single argument for on-device processing over a cloud face API.
  • Teacher trust and pushback around biometric surveillance — needs honest communication about what's stored and why, not just a rollout notice.
  • The spoofing arms race is never "solved." Treat every anti-spoofing measure as raising the cost of cheating, not eliminating it outright.

14 — MVP

The simplest version worth actually building

Login (already built) + a GPS reading with its accuracy + the server recomputing the geofence distance itself + a selfie captured as stored evidence (not yet algorithmically matched) + a server-stamped timestamp + one record with a status an admin can review.

No face matching, no liveness, no device binding yet. This alone removes the most common form of cheating — marking attendance from home — without any of the cost, false-reject risk, or privacy weight that biometrics bring. It's also the fastest path to learning whether the fancier steps are even needed.

15 — Roadmap

What to add later, and in what order

Phase 2

On-device face matching. Compare embeddings only; keep it human-reviewable rather than auto-rejecting on a borderline score.

Phase 3

Active liveness. One random simple prompt, added only once face matching is live and worth protecting.

Phase 4

Device binding + anomaly detection. Impossible-travel checks, repeated-flag patterns, recognized-device enforcement.

Build each phase once the previous one shows a real, measured gap — not ahead of evidence that it's needed.

16 — Separate from the core flow

Ideas specifically for Indian government schools

These aren't part of the verification flow itself — they're what would make the system genuinely usable in this specific context, worth considering alongside it:

  • Offline-first by default, not offline-tolerant — a local queue and background sync is core infrastructure here, not a nice-to-have.
  • A low-bandwidth mode — compress the selfie heavily or defer photo upload on 2G, syncing full evidence once on wifi.
  • Regional-language UI and voice prompts, for lower digital literacy audiences.
  • Integration hooks with existing state systems (e.g. UDISE+, Shala Darpan / a state SDMIS) so schools aren't doing double data entry.
  • An SMS or missed-call fallback for genuinely zero-connectivity days — heavily flagged for review, as a last resort only.
  • Guest/proxy-teacher support, common in under-staffed schools, with explicit admin approval rather than being treated as fraud by default.
  • Design for cheap Android phones as the baseline, not high-end devices — this shapes camera, GPS, and battery/data assumptions throughout.

17 — Recommendation

Recommended end-to-end architecture

Mobile app (the existing Expo app in mobile/) captures raw evidence only — GPS + accuracy, a selfie in phase 2+, device id, client timestamp — and does only fast local checks for instant feedback (e.g. "accuracy too low, retry") before sending anything. It never decides pass/fail on its own.

It sends that evidence to a new endpoint on the existing server (Express + Prisma, in server/), authenticated with the JWT session that already exists. The server loads the school's stored geofence, recomputes the real distance, checks the accuracy threshold, and — from phase 2 onward — runs the face match itself against the stored enrollment. It stamps its own timestamp and writes one attendance record with a verified / flagged / rejected status and a reason.

New data conceptually needed (not being built yet): geofence fields on School, a new attendance-record model, a face-enrollment model in phase 2 (storing the embedding rather than the raw photo where possible), and a device model in phase 4.

Why this shape

  • It reuses the auth, session, school, and role system that's already battle-tested in this codebase, instead of building a parallel one.
  • It keeps the "server never trusts the client" rule that this codebase already applies to auth and role checks — the same discipline, applied to a new feature.
  • On-device face/liveness processing keeps the recurring cost near zero at government scale and works with no internet — the single most important constraint for this specific audience.
  • Shipping in phases means real value — an honest, GPS-and-evidence-backed attendance system — lands in weeks, not after months spent building a full biometric pipeline that the honest-evidence version might make unnecessary in the first place.

18 — Working-time system

School timing rules and the check-in window

Three separate clock boundaries do different jobs, and mixing them up is where most attendance systems get confusing. Keep them distinct:

  • Opening / closing time — when the school day formally starts and ends. This is the anchor everything else (late, early, required hours) is measured against.
  • Check-in window — the range of time the app will accept a check-in as a normal, same-day event at all (e.g. 8:30–10:00 for a 9:00 opening). Arriving before it isn't penalized — early is simply on-time. Arriving after it isn't silently rejected either — it's still recorded, just held for a human decision instead of auto-approved (see §19).
  • Required working time — how long a teacher is expected to be present, used to work out shortfall and half-day. By default this equals the school day's duration (closing − opening), not a separate number — see the policy note in §19.

All three need to be configurable per school, per weekday, with two real-world extras: a date-specific override (a declared holiday, a half-day for an exam, a one-off early closure) and an effective-date range (many states shift school hours seasonally — summer timing vs. winter timing — so "Monday's timing" isn't a single permanent value, it can change from a given date onward).

19 — Working-time system

How Present, Late, Absent, Half-day and shortfall get calculated

Policy choice worth deciding explicitly

Should a teacher who arrives late but stays late "make up" the lost time, or is being present for the full 9:00–4:00 window the actual requirement regardless of total hours? Most government service-rule conventions use the second model — a fixed window, with late arrival and early departure tracked as their own separate facts, not netted against each other. That's the default recommended here (compensateLateWithStay: false), kept as a per-school config flag rather than hard-coded, since some institutions do allow the trade-off.

Arrival classification

Check-in timeClassification
At or before opening timeOn-time. No flag.
After opening, at or before window closeLate — recorded minutes late. Still Present.
After window closeRecorded, but held as Flagged — outside window, pending an admin decision (Present-late / Half-day / Absent). Never auto-approved as a normal Present.

A small configurable grace period (5–10 minutes) before "Late" kicks in is a reasonable real-world default — arriving 3 minutes after the bell shouldn't read the same as arriving 40 minutes after it. Left as an off-by-default config knob so the numbers below stay literal.

Working time and thresholds

TermHow it's worked out
Working minutesCheck-out time − check-in time. Raw elapsed time; no break deduction in the base model.

Half-day thresholdA configurable fraction of required time (e.g. 50%). Below it → Half-day.
Full-day graceA small buffer near 100% (e.g. within 15 minutes) still counts as a full day — a teacher shouldn't lose "full day" status over walking-to-the-gate rounding.

Shortfall and early-departure are two views of the same underlying gap, not two separate penalties — show them together on one record rather than double-counting.

22 — Working-time system

Real-world cases worth adding to the list

  • On-duty elsewhere. The single most important addition — Indian government-school teachers are routinely pulled for election duty, census work, training, cluster meetings, or invigilation at another school. Without a distinct "On duty" status, the system will constantly and wrongly flag extremely normal days as Absent or unexplained.
  • Approved leave. A day with sanctioned CL/EL/medical leave should never be computed as Absent just because there's no check-in — it needs its own status that a leave-management process (even a simple one) can set.
  • Declared holidays and school closures. Attendance shouldn't be expected — or computed as Absent — on a day the school was officially closed.
  • Pre-approved early leave / half-day. A teacher with prior permission to leave early for a specific reason shouldn't generate the same flag as an unapproved early departure — the record needs an "approved" note, not just a raw timestamp gap.
  • Seasonal timing changes. Many states shift school hours between summer and winter — timing configuration needs an effective-date range, not a single permanent weekday value (already covered in §18's config).
  • Shift schools. Two schools sharing one campus in a morning/evening shift is common — same geofence, different timing windows depending on which school (and shift) the teacher belongs to.
  • Duplicate check-in taps. An accidental double-tap should update the same record, not create a second one.
  • Server unreachable at the exact check-in moment. Same handling as losing internet mid-day — queue locally, sync automatically, don't lose the evidence.

The recommended model, in one place

1

School timing rules. Per school, per weekday, with date-specific overrides for holidays/half-days and an effective-date range for seasonal timing changes.

2

Check-in window. Opens before opening time, extends a defined grace past it. Inside it: always accepted. After it: still recorded, held for admin review rather than auto-approved.

3

Late-arrival rule. Any check-in after opening time (optionally past a small configurable grace) is marked Late with exact minutes recorded; still counts as Present.

4

Check-out rules. One check-out event, same evidence bundle as check-in. A duplicate tap updates the existing record rather than creating a new one.

5

Early-departure rule. Checkout before closing time (minus a small grace) is flagged with exact minutes recorded, feeding the same shortfall figure rather than a separate penalty.

6

Minimum working-time rule. Required time = that weekday's school-day duration by default. Below a configurable half-day threshold → Half-day; below full (with a small grace) → Present with shortfall flagged; at or above → Full day.

7

Absent rule. No check-in and no approved leave/holiday/on-duty record for that date → Absent. Any of those records present → never auto-Absent.

8

Missing check-out handling. End of day with no checkout → "Pending regularization." Arrival classification stands; working time and shortfall stay unresolved until confirmed — never silently assumed as a full day.

9

GPS/location strategy. Approach D — check-in and check-out only, plus rare pattern-triggered spot-checks. No continuous or scheduled background tracking.

10

Offline handling. Evidence is captured and timestamped on-device, queued locally, synced automatically once online. Offline submissions are lightly flagged, never penalized outright.

11

Suspicious-activity handling. Mock-location flags, impossible-travel patterns, or repeated flags on one account escalate to a spot-check or the admin queue — never silently rejected, never silently approved.

12

Admin review/fallback. Every flagged case lands in one review queue, resolved with a one-tap decision and a logged reason — never edited silently.

13

What's stored. Raw check-in/check-out evidence as the source of truth, plus computed fields (status, late/early minutes, working minutes, shortfall) recalculated by one shared function whenever an input changes — the same discipline this codebase already uses for classroom attendance percentages, applied here instead of reimplemented per route.

14

What the teacher sees. Today's live status in plain language, a monthly calendar of day-by-day status, a running summary of lates/shortfalls, and any flagged item explained with a clear next step — never a bare error.

15

What the admin sees. A same-day dashboard of who's present/late/absent/flagged, a dedicated review queue, the school timing configuration screen, and exportable monthly reports.

Research and design exploration only — no code changes were made to the Teacher Assistant codebase as part of this document.
